3.5 Cloud Layer — Deferred Infrastructure

Status: ❌ NOT REACHABLE

Why it's not connected:
  1. Network isolation: Per-session containers live on ephemeral chainbreak-net-<sessionId>; never attached to localstack-net.
  2. Environment mismatch: docker.service.js::provision() doesn't inject AWS_ENDPOINT_URL=http://localstack:4566 into per-session containers.
  3. Empty init script: LocalStack/init-aws.sh is 0 bytes — no S3 buckets, IAM roles, or EC2 resources are provisioned.
  4. Architectural choice: Deliberately deferred until infrastructure can be safely isolated. Mounting /var/run/docker.sock into an RCE-vulnerable container (as Challenge 2 currently does) is a real host-compromise path if cloud layer is connected.

Roadmap to Enable Cloud Layer

Priority 1: Network Wiring
Modify docker.service.js::provision() to attach workstation container to localstack-net via docker.getNetwork('chainbreak-localstack-net').connect(container).
Priority 2: Environment Injection
Wire AWS_ENDPOINT_URL into per-session `Env` array per-challenge, so aws-cli knows to talk to LocalStack instead of real AWS.
Priority 3: LocalStack Initialization
Populate LocalStack/init-aws.sh with realistic S3 bucket + IAM role creation, seeded with intentional misconfigurations (public read on sensitive bucket, overpermissioned role, etc.).
Priority 4: Security Isolation (Challenge 2 blocker)
Challenge 2's RCE cannot mount docker.sock while connected to cloud network — risk of attacker pivoting to host. Either: (a) remove docker.sock entirely (safest), (b) connect to cloud network only after RCE stage, or (c) use Pod Security Policies / Seccomp to restrict syscalls.

4.3 Lessons Learned & Design Patterns

✓ Session Isolation Pattern

Lesson: Per-session ephemeral Docker networks + containers are essential for preventing learner cross-contamination and enabling concurrent multi-learner deployments.

Implementation: docker.service.js::provision() creates unique network per session ID; TTL reaper cleans up on expiry.

✓ Flag Injection via Environment

Lesson: Injecting plaintext flags at container-create time, with bcrypt hashing at seed time, decouples challenge creation from flag management.

Challenge: Manual sync between docker.service.js and seed.js is error-prone — both must be updated for flag changes.

❌ Socket.IO Room-Based Cleanup

Lesson: Code that calls io.in('session:...').disconnectSockets(true) is dead code — no socket joins that room, so reaper can't proactively close learner terminals.

Better Pattern: Track socket → session mapping; explicitly disconnect socket when tearing down session.

❌ Non-Running Session Leak

Lesson: Reaper only sweeps `status='running'`. A crash between container creation and the DB write leaves orphaned containers.

Fix: Also sweep `status='provisioning'` and `status='failed'` with age-based TTL; add container labeling to enable orphan discovery outside normal session lifecycle.

△ Workstation Image Complexity

Lesson: Multi-stage Dockerfile to compile John the Ripper (Debian's packaged version lacks SSH support) is necessary but adds build time.

Trade-off: ~5 min build vs. ~30 years of trying to use wordlists with non-SSH-capable john. Worth it.

△ AWS Creds in File, Not Env

Lesson: Planting AWS credentials in `/root/.aws/credentials` (file, 600) rather than as env vars teaches real-world escalation path (privilege → FS read → cred discovery).

Challenge: Makes per-session unique creds harder (would need per-session file generation at container init).

Proposed Study Design: Randomized controlled trial with 15–20 cybersecurity students/practitioners.

Control Group (n=7–10): DVWA or OWASP Juice Shop (single-layer, standard baseline).
Treatment Group (n=7–10): ChainBreak Challenge 1 + Challenge 2 (tri-layer attack chain).
Sub-treatment (if feasible): AI hints enabled/disabled within treatment group to isolate hinting effect.
Primary Outcome: Pre/post skill assessment (OWASP exploitation, container security, cloud misconfig understanding). Measured via:
  • Practical scenario (given vulnerable app, design exploit chain) scored by rubric.
  • Multiple-choice conceptual knowledge (OWASP, Docker, AWS categories).
  • Time-to-solution on novel, unseen challenge (transfer learning test).
Secondary Outcomes:
  • System Usability Scale (SUS) survey.
  • Cognitive Load Assessment (NASA TLX).
  • Semi-structured interviews (perceived learning, motivation, confusion points).
Sample size calculation: Cohen's d = 0.8 (medium-to-large effect), α = 0.05, β = 0.2 (80% power) → n ≈ 17 per group. Current target (15–20) is on boundary; recruitment buffer of +2–3 per group recommended.

Objective 5: Transferable Design Principles for Tri-Layer CTF Development

7.1 Pedagogical Principles

1. Attack Chain Coherence

Principle: Each layer's exploit should depend on artifacts from the previous stage, not exist in isolation.

Example: Challenge 1's SSH key is only discoverable via path traversal (web layer); its passphrase is only crackable with a curated wordlist (container layer); the AWS creds found post-escalation are only consumable if cloud layer is connected (future).

Benefit: Forces learners to internalize cause-and-effect across layers; matches real-world attack chains.

2. Privilege-Gated Artifacts

Principle: Plant flags and secrets behind real privilege boundaries (file perms, OS-level escalation), not as hints or breadcrumbs.

Example: `/root/flag.txt` (600) requires real SUID escalation; AWS creds require reading a 600-permission file as root.

Benefit: Confirms that learning is genuine exploitation, not treasure-hunt guessing.

3. Scaffolding Through Visualization

Principle: Provide immersive, real-time UI (kill-chain graph, fractional progress rings, live flag ticking) that orients learners without spoiling solutions.

Example: Kill-chain node fills from 0% → 100% as each flag in a layer is captured; learner sees "container layer 33% complete" but not which specific flag is next.

Benefit: Reduces cognitive load; maintains intrinsic motivation.

4. Per-Session Isolation & Concurrency

Principle: Every learner gets ephemeral, isolated containers on a unique network. No shared state, no cross-contamination.

Example: 20 learners can run Challenge 1 simultaneously; each has its own target + workstation, with own SSH key and AWS creds environment.

Benefit: Enables classroom deployment; scales to arbitrary learner cohorts without infrastructure bloat.

5. Adaptive Hinting (Planned)

Principle: AI hints adapt to learner progress, failed attempts, and context. Socratic method: ask questions instead of giving answers.

Example: After 5 failed SQLi payloads, hint: "Have you considered that the input is concatenated into a WHERE clause? What character could break that syntax?"

Benefit: Accommodates skill variance; keeps less-experienced learners from ragequitting.

6. Real Tools & Real Shells

Principle: Use genuine, industry-standard tools (curl, ssh, john the Ripper, aws-cli) in real shells, not gamified simulators.

Example: Learner SSH-es into target with an actual leaked key. Post-exploitation runs a real SUID binary, not a "press here to escalate" button.

Benefit: Skills transfer directly to penetration testing engagements; no re-learning curve for tool syntax.

7.2 Technical Design Patterns

Pattern Rationale Implementation (ChainBreak)
Ephemeral Per-Session Networks Guarantees learner isolation; enables concurrent deployments; simplifies cleanup (remove network = remove all attached containers). docker.service.js::provision() creates chainbreak-net-<sessionId>; reaper removes on TTL expiry.
Environment-Based Flag Injection Decouples flag distribution from platform code. Enables dynamic flag rotation (future: per-session unique flags). Challenge targets read $FLAG_1, $FLAG_2 etc. at startup; fallback to hardcoded literal for standalone testing.
Stateless Terminal Bridge Socket.IO connection + node-pty subprocess is ephemeral and tied to session lifecycle. Terminal closes when session expires. server/socket/terminal.js spawns docker exec pty; ptyProcess.onData scans for flags in real time.
Regex-Based Flag Capture Agnostic to where flag comes from (HTTP response, file read, SSH banner). Captures across all output streams. FLAG_PATTERN = /flag\{[A-Za-z0-9_-]{4,64}\}/g scanned on every `ptyProcess.onData` chunk.
Bcrypt Hash Storage Never store plaintext flags in database. One-way hash ensures even a DB breach doesn't leak solutions. seed.js hashes all flag plaintexts at seed time with `bcrypt.hash(flag, 12)`.
TTL-Based Reaper Automated cleanup prevents resource leaks at scale. Configurable TTL (default 60 min) matches classroom session length. reaper.service.js sweeps every 60s; tears down containers + networks for expired sessions.

7.3 Future Roadmap (Objective 5 Synthesis)

Phase 2: AI-Adaptive Hinting (Priority 1)

Objective: Integrate LLM-backed hints to measure whether adaptive guidance improves learning outcomes for less-experienced learners.

  • Capture learner context: flags captured, attempts (successes + failures), time-on-challenge, terminal commands.
  • Design Socratic prompts: "What information would help you move to the next layer?" instead of "Try SQLi".
  • Rate-limit hints (1 hint per 2 min) to prevent solution-dumping.
  • A/B test: hints vs. no hints within treatment group.

Phase 3: Complete Cloud Layer (Priority 2)

Objective: Wire per-session containers to LocalStack; create realistic S3/IAM misconfigurations; implement cloud-layer flags.

  • Network: attach workstation to localstack-net post-provision.
  • Credentials: inject AWS_ENDPOINT_URL + IAM role ARN into per-session environment.
  • Init: populate LocalStack/init-aws.sh with intentional misconfigurations (public-read bucket, overpermissioned role).
  • Flags: implement S3 exfiltration + IAM privilege escalation scenarios (Challenges 1 + 2).

Phase 4: Kubernetes Attack Chains (Future Differentiator)

Objective: Extend tri-layer model to Kubernetes: web exploit → pod escape → cluster RBAC abuse → cloud API abuse.

  • Replace Docker containers with per-session Kubernetes namespaces.
  • Challenge: compromised pod with service account token; escalate to cluster-admin via RBAC misconfiguration.
  • Differentiator: no other educational platform currently offers this end-to-end K8s attack chain.

Phase 5: Azure Cloud Misconfiguration Scenarios

Objective: Replicate Challenge 1–2 patterns on Azure infrastructure (via Terraform or Bicep + Azure Stack Hub emulator).

  • Azure-equivalent misconfigurations: overpermissioned MSI, leaked storage account keys, exposed Key Vault secrets.
  • Enables multi-cloud comparative learning (AWS vs. Azure patterns).
